# ECHO大模型辅助设计协作记录


## 一 协作目标与职责
以45项声学功能在Zynq-7020上的共享执行为主线，大模型用于计算图拆分、微程序和接口分析、验证方案及性能归因；工程人员负责需求取舍、结果复核与验收。模型建议经过源码、工具输出或固定输入比较后才纳入设计。

## 二 智能体工作流设计
需求与冻结边界 → 主智能体拆解设计问题 → 读取源码与基线 → 提出一个有界方案 → 本地工具执行或静态核查 → 比较结果与证据 → 通过则纳入版本，失败则定位或回退 → 提炼可复用技能。

| 角色 | 输入 | 输出与约束 |
|---|---|---|
| 工程人员 | 应用目标、板卡条件、使用反馈 | 决定功能范围和验收条件 |
| 主智能体 | 源码、数据、报告及任务约束 | 形成设计方案、修改建议和验证入口，不直接以回答代替验证 |
| 本地工具 | 明确文件、输入及命令 | 提供编译、仿真、周期、资源和结果文件；工具不是另一个决策模型 |
| 审查与验收 | 方案及实际输出 | 核对功能、结果、资源、实时性与版本，失败保留基线 |


## 三之1 共享计算架构与软硬件划分

**设计问题**
目标器件为Zynq-7020，需要实现多种声学分析功能，同时保留实时采集、小屏显示和PC调用。若按功能逐项复制计算通路，会重复配置变换、统计和访存资源。

**设计提示词**
请依据六通道48kHz输入、7020资源和45项活动功能，按公共运算拆分计算图。给出专用核、可编程核、存储和PS管理的边界；优先复用，不删减功能，不把声学计算转移到PS或PC。列出共享引入的调度代价及接口约束。

**模型方案摘要**
将FFT/IFFT等固定结构运算集中到一个专用模块，将功率统计、频带累计、对数、归一化和判断等交给可编程标量核。输入、程序、中间结果和输出使用共享DDR区域；PS承担配置、通信和文件管理，PC负责解码与显示。通过任务计划组织计算顺序，而不是为每项功能实例化完整硬件。

**工程核查与依据**
以实际stream_fft2048、scalar_engine及板级工程核对计算边界。最终FFT/IFFT及包装使用8419 LUT、标量核9941 LUT；整板40127 LUT。两核之间由调度及共享存储协同，不能画成一条未经实现的直接数据连接。

**纠错与方案收敛**
设计表述从“多个功能模块并列”收敛为“公共计算步骤复用”。资源对照中，独立模块A/B仍是估算，不能作为另一个已综合设计或精确节省率。共享减少复制，但会增加排队及状态管理开销。

**最终采用**
采用一套变换模块加一套可编程标量核；保留采集、FIFO、调度、事件及接口等独立逻辑。新增功能首先判断能否映射到现有微程序与数据通路。

## 三之2 频谱基础计算与统一数值定义

**设计问题**
FFT、功率谱、PSD、STFT及电平共用输入。如果窗函数、单边谱系数、频率坐标或采样率不一致，会出现核计算正确但结果含义或图表位置错误。

**设计提示词**
请统一2048点PCM分析的输入格式、去均值、Hann窗、FFT缩放、单边幅度、功率和PSD定义。区分单窗PSD、多窗平均与STFT。检查真实采样率、频点索引和通道布局，给出最小数学对照，不另建重复计算核。

**模型方案摘要**
PCM模式先归一化、去均值并加周期Hann窗，再计算FFT。由复数模平方产生功率；PSD除以采样率与窗能量，普通单边频点乘2，直流与奈奎斯特频点不翻倍。连续时间窗口的频谱加时间戳构成STFT；需要谱平均时另外保留统计状态。

**工程核查与依据**
实际代码使用2048点周期Hann窗，窗能量为768，PSD系数为1/(fs×768)。实际采样率约48009.775Hz；完整输入、参考与原生输出在软件测量目录按功能关联。

**纠错与方案收敛**
纠正“有FFT就等于完成所有频谱显示”和“单窗PSD可直接称为Welch”的泛化。频率轴与数据布局属于结果链的一部分；STFT时间列不能用界面刷新时间冒充采样时间。

**最终采用**
保留共享FFT模块已具备的谱及电平后处理；统一单位和坐标定义。不同显示形式复用数据，但不混用幅度、功率和功率密度。

**对应设计文件与证据**

## 三之3 长任务分段执行与上下文设计

**设计问题**
一个标量核需要服务实时和后台功能，长循环可能持续占用计算资源；仅限制程序长度也不能限制带循环算法的完整执行量。

**设计提示词**
请设计有界微程序执行与恢复机制，保存寄存器、程序位置和任务身份。说明每次指令预算、完整程序长度与总执行量的区别，并检查暂停期间输入覆盖、配置变更和错误恢复风险，不以固定指令条数等同固定周期。

**模型方案摘要**
每次按预算执行，达到边界后保存现场，后续恢复。以32个浮点寄存器、32个整数寄存器及16个控制字组成80字上下文。长数组留在DDR；上下文绑定程序、输入输出、配置和任务代次，避免把旧现场用于新任务。

**工程核查与依据**
代码限定单次预算不超过512条、静态程序长度不超过1024条。80个32位字合计320字节，保存一个任务现场；循环累计执行量可以超过512条。

**纠错与方案收敛**
512条不是512个时钟，也不是最多512个算法。上下文恢复不等于任意时刻抢占，更不等于自动识别重复结果并复用。共享中间结果需要调度和程序明确安排，恢复时也必须保证数据仍有效。

**最终采用**
保留有界批次和上下文机制，为P0优先与后台计算协同提供基础。任务切换在可用执行边界进行，具体实时性以周期和负载证据判断。

**对应设计文件与证据**
- `src/project/deployment/work_platform_20261013/phase15_analysis_only_20261023/integration/shared_backend/scalar_engine.cpp`
- `sim/inherited_results/performance_resource_comprehensive_20261025/SUMMARY.json`

## 三之4 不增加硬件资源的执行开销优化

**设计问题**
共享核中存在程序提交、状态轮询和上下文写回开销，直接增加并行运算单元可能花费较多资源，却无法有效减少这些固定开销。

**设计提示词**
请基于目标板周期记录找出一个主要开销。在固定输入、程序和计算顺序下，只改变单次执行预算，比较64条与512条的执行时延、输出一致性、调用次数及P0影响。不要将采集或PC绘图时间混入内核加速比。

**模型方案摘要**
优先增加每次有效计算量，减少切片提交和现场写回。对多个代表任务正反顺序配对，保留每次执行周期和输出，同时观察实时任务的漏窗、丢样及失败计数。若结果不一致或实时性受损，则拒绝该参数。

**工程核查与依据**
历史7020板测中，谱平滑的12289条动态指令由193次调用降为25次，少168次现场写回，按每份320字节计减少53760字节。当前保留的7组任务共28次配对，执行阶段中位时延下降15.76%～74.68%，26372个比较输出字逐字一致，同一Bitstream硬件资源增量为0。

**纠错与方案收敛**
加速结论限定于执行阶段及对应任务；不能将最高降幅写成全系统加速，也不能以短时间P0并发记录替代全部功能长期负载保证。优化板测与最终接口硬件的版本分别保留。

**最终采用**
采用已经验证的预算配置；不为少量增益继续复制硬件。保留固定输入、原始周期、逐字比较及版本信息，作为性能评分的直接证据。

**对应设计文件与证据**
- `sim/inherited_results/performance_resource_comprehensive_20261025/SUMMARY.json`

## 三之5 功能调用与多阶段任务状态设计

**设计问题**
功能有PL计算实现，并不意味着PC已能正确启动和读取。输入准备字段、结果身份、阶段推进及界面进度只要有一处不一致，就可能出现超时、无数据或错误完成状态。

**设计提示词**
请沿featureId→执行计划→输入准备→PL启动→结果发布→网关解码检查通路。区分当前阶段索引与已完成阶段数。结果必须匹配任务及配置；不能由进度条达到100%推断结果有效，也不能在PC补算缺失结果。

**模型方案摘要**
PC通过48120控制通道启动和查询任务，48121传输二进制数据。网关按计划检查输入、装载程序、推进阶段并恢复配置。用session、config、generation及sourceFrame等字段识别结果；将运行进度、任务完成和数值有效作为不同状态处理。

**工程核查与依据**
最终注册表有45个活动功能；本次交付核查784处计划文件引用均存在。执行计划、输入及结果布局可在源树注册表和网关实现中对应。此项是目录与依赖核查，不等同45项全部实物声学验收。

**纠错与方案收敛**
明确“缺接口”与“缺算法”不同；currentStageIndex从0开始，completedStages表示已完成数量。输入长度和偏移必须来自有效计划，不能由界面静默猜测。

**最终采用**
保持对外功能协议稳定，把内部调度变化封装在设备侧。多阶段任务在结果完整后推进，停止及失败路径均处理配置和资源恢复。

## 三之6 背景学习与异常事件数据闭环

**设计问题**
用户需要在规律设备噪声或背景声中发现明显变化，并取得事件前后音频。若仅由PC低频轮询电平，短促事件可能被遗漏；如果触发后才开始录音，又无法保留事前片段。

**设计提示词**
请将事件监测拆为背景学习、持续判断、触发、前后片段关联、持久化及下载。区分特征流和原始PCM路径，检查事件合并、缓存释放、背压和失败状态。用户关闭前持续监测，不能把触发标志当成文件保存成功。

**模型方案摘要**
PL根据电平和频带摘要学习背景，并判断能量变化、声音中断及频带变化。原始PCM同时进入缓存，事件关联采样范围；PS保存片段与元数据，PC按事件获取并导出。各阶段独立保留状态及错误信息。

**工程核查与依据**
事件检测器输入是六路功率与频带特征，不是直接输入PCM；录音来自并行原始数据路径。网关和文件服务承担持久化与下载。记录中的各角色应与实际模块对应。

**纠错与方案收敛**
明确区分“检测到事件”“片段完整”“文件已保存”和“下载成功”，避免一个界面状态代表全部闭环。这是状态设计与审查约束，不将未执行的长期事件测试补写为通过。

**最终采用**
保留板端持续检测和原始缓存路径，主机负责操作与导出；按事件关联音频及数据，后续改动保持生命周期和接口契约。

## 四 从协作中提炼的复用方法

1. 先识别公共计算和固定开销，再决定是否增加并行硬件；使用固定输入和成对板测确认收益。
2. 以任务身份、数据生命周期和结果有效性约束共享执行，不用界面状态代替设备完成。
3. 对数学、RTL、接口及实物声学分层记录证据，源码存在、能够调用与实际验收分别判断。
4. 只修改明确受影响的环节，先最小复现，再局部回归；无净收益则停止或回退。

上述方法已整理为skill目录中的三个技能包。它们可用于其他FPGA与嵌入式测量工程，使用者需替换器件、接口和评价条件，不照搬本项目指标。
